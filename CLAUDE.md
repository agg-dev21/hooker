# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hooker is a Unity **6000.6.5f1** 2D action platformer (URP, new Input System, TextMesh Pro) built around a grappling hook. Story: MainMenu → Tutorial 1–7 → four boss levels connected by a boat scene → Ending_Grave. All code is C#; there is no package/build tooling outside Unity.

`Docs/CodeStructure.md` is the folder-by-folder map of the code and the coding conventions. Read it before adding or moving files.

## Commands

**Compile check without opening Unity** (the `.csproj` files are SDK-style, generated by Unity, gitignored):
```bash
dotnet build Hooker.Editor.csproj -nologo -v q    # builds Hooker.Runtime too (~20 s)
dotnet build Hooker.Runtime.csproj -nologo -v q   # gameplay code only
```
- The build should finish with 0 errors. One warning is known and expected: `DevSettings` uses the deprecated `DEVELOPMENT_BUILD` directive.
- The `.csproj` files only list files Unity knew about when it last regenerated them. A **newly created** `.cs` file isn't compiled until Unity regenerates the project, so its errors only show up in the Unity Console.

**Tests:** `com.unity.test-framework` is installed but there are **no tests yet**. Batch-mode runs only work when the project is *not* open in the editor:
```bash
"/c/Program Files/Unity/Hub/Editor/6000.6.5f1/Editor/Unity.exe" -batchmode -projectPath . -runTests \
  -testPlatform EditMode -testResults Temp/results.xml [-testFilter <Namespace.Class.Method>]
```

**Running the game:** open `Assets/Scenes/MainMenu.unity` in Unity and press Play (or open any level scene directly). In the editor and in Development Builds, `DevTools` gives these keys:
- F1: push every boss to phase 2, press again to kill it
- F2: heal to full
- F3: god mode
- F4: skip to the next scene

Turn them on or off with `Assets/Resources/DevSettings.asset` or Tools > Dev Tools.

## Architecture

### Scenes are generated by editor code
Most scenes are **built by editor scripts** in `Assets/Editor`, run from the Unity **Tools** menu. They aren't built by hand.
- `Tools/Other/Rebuild Levels (wipes changes)/...` builders (`Editor/Builders`) delete the scene and rebuild it from `Assets/Scenes/Room_Template.unity` with `LevelKit.NewSceneFromTemplate`. Then they paint tiles and place platforms, hazards, enemies and bosses. Each builder's header comment describes the level's layout (x-ranges per section).
- `Tools/Art/...` (`Editor/Art`) slices the sprite sheets in `Assets/Art/<Character>/` and puts the frames and sizes onto objects in specific scenes. The header comment of each tool lists its sheets and frame sizes.
- `Tools/Other/Balance/...`, `Level N Boss/Make Harder` (`Editor/Balance`) rewrite serialized boss numbers in the scenes.
- The Tools menu is laid out for art work: `Tools/Update All Art` (`Editor/Tools/UpdateAllArt.cs`) is at the top, then Dev Tools, then the `Tools/Art/...` tools grouped by priority (characters 100s, effects and UI 120s, world 140s). Everything that isn't art lives under `Tools/Other/...` (priority 3000).
- `Tools/Update All Art` runs every art tool in order and shows one summary. Art tools report through `EditorKit.Message` (not `EditorUtility.DisplayDialog`) so their messages are collected during that run. **Add any new art tool to `UpdateAllArt.Steps`** and give its `MenuItem` a priority in its group.
- `Tools/Other/Set Up All Art And Jail` (`Editor/Tools/SetUpEverything.cs`) runs the art tools plus the non-art setup steps (jail, story dialogue, hint scrolls). Add any new non-art setup tool to its `Steps` array.

So to change a level's layout, **edit its builder and re-run the menu item**. Hand edits to a scene are lost on the next rebuild. Don't edit `.unity`, `.prefab` or `.meta` YAML directly.

### Game flow and saves: `RunOrder`
`Core/RunOrder.cs` (a static class) owns the level order and all story progress, saved in `PlayerPrefs` (`run.*` keys). Every scene change goes through `RunOrder.Resolve(requested)`, called by `SceneExit`, `BoatExit` and `ScreenFade`. A scene asks for a fixed name, and `Resolve` remaps it based on progress, e.g. tutorial → Level_1, boss room → boat (`Level_1_Sail`) → next level. Its header comment is the clearest description of the whole game flow.
- Boss-earned unlocks (`PlayerAbility`, `PlayerChain`, `PlayerUpgrades`, `Companion`) save their own `PlayerPrefs` keys. **A new persistent key must also be cleared in `RunOrder.NewGame()`.**
- `EnsureScenesInBuild` (editor, `[InitializeOnLoad]`) keeps MainMenu first and Ending_Grave in the Scene List. New scenes need `EditorKit.AddToSceneList`.

### Bosses
Class names differ from character names:

| Character | Scene | Class |
|---|---|---|
| Hardy | `Level_1_Deck` | `HardyBoss` |
| Oscar (poison lizard) | `Level_2_Boss` | `PoisonBoss` |
| Madame O | `Level_3_Boss` | `OctopusBoss` |
| KK (the father) | `Level_4_Boss` | `FatherBoss` |

When two bosses fight at once, they share attack timing through the static `BossTurns`. Each boss's header comment lists its attacks and phases.

### Cross-cutting systems
- **Input:** all player input goes through `Core/GameInput` (the `GameAction` enum). Bindings can be changed in the pause menu and are saved. Gameplay code should read `GameInput`, not `Keyboard.current` or gamepads directly. `DevTools` is the only exception.
- **Tuning data:** ScriptableObject settings live in `Assets/Resources/` and are loaded by name with `Resources.Load`: `PlayerBalance`, `ItemSettings`, `CompanionSettings`, `FallDamageSettings`, the `*Art` assets, `HealthBarSkin` and `DevSettings`. Renaming one of these assets breaks loading. Boss and enemy numbers are serialized fields on the components in the scenes.
- **Damage:** `Combat/Health` is used by both the player and enemies. Items change damage through `Health.DamageFilter` and `Health.BeforeDeath`, which `PlayerItems` sets.
- **Time scale:** pausing and winning set `Time.timeScale = 0`, and `GameManager.IsPausedOrWon` reports it. The `GameFeel` hit-stop deliberately slows time to `0.05`, **not 0**, because 0 means "paused" to the rest of the code.
- **Static state:** static systems install or reset with `[RuntimeInitializeOnLoadMethod]` (e.g. `DevTools.Install`, `BossTurns.ResetOnPlay` at `SubsystemRegistration`), so they stay correct when Domain Reload is off. Do the same for any new static state.
- **UI built in code:** most UI, including the pause menu (`PauseMenu.Create`), is built at runtime with `UI/UiKit` (`using static UiKit;`).
- **Dev-only code:** `DevSettings.On` is always `false` in non-development builds. Put any testing-only behaviour behind it.

## Conventions (from Docs/CodeStructure.md, plus observed style)
- Assemblies: runtime code goes in `Assets/Scripts` (`Hooker.Runtime`). Editor tools go in `Assets/Editor` (`Hooker.Editor`, editor-only, references Runtime). Runtime code that uses `UnityEditor` must be wrapped in `#if UNITY_EDITOR`.
- Partial classes: when a class gets past ~500 lines, split related methods into `Class.Part.cs` in the same folder (e.g. `HardyBoss.Attacks.cs`). Inspector fields, lifecycle methods and reset/death logic stay in the main `Class.cs`.
- Moving a script: always move its `.meta` file with it, or references in scenes break. Don't rename `[SerializeField]` fields without `[FormerlySerializedAs]`.
- Editor helpers used by more than one tool go in `Editor/Shared/EditorKit` or `LevelKit`.
- Comments: every file starts with a plain-English header comment saying what it does, how to use it and, for editor tools, which menu item it adds. Inline comments are short and plain. Keep this style.
